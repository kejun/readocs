# Wi-Fi 配网优化方案

日期：2026-10-26  
状态：待实施、待真机验收  
分析基线：`master` / `247a630390531e7f04d83eda8839733351ae4a9c`，源码固件标识为 `readocs-0.2.6`。  
本次交付：仅新增方案文档，不修改固件、代理、配置或测试，不构建和烧录设备。

## 1. 问题与目标

用户已连接设备的 Readocs 热点，手动打开 `http://192.168.4.1/`，页面显示：

> Use the device setup hotspot

该文字由固件网页入口的 HTTP 403 分支返回。请求已经到达网页服务，但 `on_ap()` 未通过，配网页 HTML 尚未发送。[S1]

首要目标是让配网会话中的合法热点访问正常进入页面，同时保留访问通道和会话检查。后续目标是让入口、提交结果和错误提示可验证、可恢复。

本方案沿用 [需求规范](spec.md) 第 9.1、9.3 节及 AC-01、AC-31、AC-32、AC-36。已有“最多五组网络、候选验证后保存、失败保留旧配置、五分钟无操作关闭”的约束继续适用。

## 2. 诊断证据与保证边界

### 2.1 已核实的事实

| 证据 | 结论 |
|---|---|
| 用户实测出现上述英文提示 | 命中网页入口的配网通道拒绝分支；单凭提示不能区分其中哪项条件失败 |
| `on_ap()` 使用 `sockaddr_in` 接收地址，并直接比较 `sin_addr.s_addr` | 实现假定 HTTP 连接的本地地址使用 IPv4 结构，没有按地址族解析，也没有检查地址长度 |
| ESP-IDF 5.5.5 的 `LWIP_IPV6` 默认开启，项目的 `sdkconfig.defaults` 没有覆盖此项 | 按仓库默认配置推断，HTTP 服务会使用 IPv6 双栈套接字；设备实际生成的 `sdkconfig` 仍需确认 |
| ESP-IDF HTTP 服务在 IPv6 开启时创建 `PF_INET6` 套接字 | IPv4 浏览器访问不等于服务器套接字一定返回 IPv4 地址结构 |
| 对应 lwIP 的 `getsockname()` 会将双栈连接中的 IPv4 地址映射为 IPv6 地址 | 地址可能以 `::ffff:192.168.4.1` 返回，不能直接按 `sockaddr_in` 读取 |

依据见 [S1]、[S2]、[S3]、[S4]、[S5]。

### 2.2 已执行的主机复现

2026-10-26，提取基线中的实际 `on_ap()` 函数，在主机创建真实 TCP 监听、连接和已接受套接字。没有替换 `getsockname()`。配网状态和 AP 地址使用替身：`model.ap=true`，AP 地址取本机回环地址 `127.0.0.1`。

两组都使用 IPv4 客户端连接同一回环地址，仅改变服务端套接字类型：

| 服务端 | 实际本地地址 | 现有代码按 IPv4 结构读出的地址 | `on_ap()` |
|---|---|---|---|
| IPv4 | `127.0.0.1` | `127.0.0.1` | `true` |
| IPv6 双栈 | `::ffff:127.0.0.1` | `0.0.0.0` | `false` |

双栈用例可触发同样的网页拒绝条件。主机测试进程退出码为 1，表示“同样的合法访问应通过”这一预期被现有实现违反，不是修复后测试通过。

该复现验证了地址结构误读机制。它不等于在 ESP32 上完成 SoftAP、DHCP、浏览器和配网保存的端到端验收。临时复现程序未加入仓库；实施时应将对应场景固化为回归测试。

### 2.3 根因判断与待确认项

**已确认存在双栈兼容性缺陷；按默认构建配置，这是与用户现象最吻合的原因。设备本次故障的最终归因仍需真机证据。**

错误链路为：

1. 浏览器访问设备的 IPv4 热点地址。
2. HTTP 服务通过双栈套接字接受连接。
3. lwIP 返回 IPv4 映射的 IPv6 本地地址。
4. `on_ap()` 使用较小的 IPv4 结构接收并解释返回数据。
5. IPv4 地址字段所在偏移对应 IPv6 的 `sin6_flowinfo`，其值为零，因此比较对象变成 `0.0.0.0`。
6. 比较失败，网页入口返回 HTTP 403。

现有 403 还可能由 `model.ap=false`、套接字地址读取失败或本地地址不匹配触发。实施前需读取实际编译配置和一次失败请求的诊断结果，确认属于哪一支。上一轮纯 IPv4 地址替身测试未覆盖双栈场景，不能作为热点通道正常的证明。

首页查询参数和手机门户探测路径也有问题，但上述 403 在路由分发前返回；应将它们作为独立问题处理。

## 3. 优先级与实施顺序

| 优先级 | 工作 | 完成条件 |
|---|---|---|
| P0 | 修复双栈地址识别，补访问检查回归与拒绝原因诊断 | 合法 IPv4、IPv4 映射 IPv6 访问通过；不合法访问仍拒绝；真机直接打开根地址成功 |
| P1 | 按 URL 路径分发请求，明确处理未知 API | 带查询参数的页面和 API 不串路由；未知 API 返回明确的 404 |
| P1 | 检查热点启动和操作入队结果，补网页连接结果反馈 | 启动或提交失败有准确提示；网页能显示连接失败并允许重试 |
| P2 | 改善手机配网门户兼容 | 选定手机系统版本可从门户进入；不支持自动弹窗时，手动访问仍可完成配网 |

先独立交付 P0，再推进 P1。P2 不作为恢复手动配网的前置条件。

## 4. P0：修复热点访问检查

### 4.1 地址解析

使用 `sockaddr_storage` 接收 `getsockname()` 的结果。检查调用结果、返回长度和地址族，再进行比较：

| 地址类型 | 处理规则 |
|---|---|
| `AF_INET` | 确认长度足够后读取 IPv4 本地地址 |
| `AF_INET6` 且是 IPv4 映射地址 | 确认长度足够后提取映射的 IPv4 地址 |
| 原生 IPv6 | 本轮没有配置和验证 AP 原生 IPv6 地址，明确拒绝；不得把任意 IPv6 地址当作 AP 访问 |
| 未知地址族、长度不足或地址读取失败 | 拒绝，并记录对应原因 |

先检查 `esp_netif_get_ip_info()` 的返回值，再读取 AP 地址。地址按统一网络字节序比较，不通过字符串包含关系或末尾字节猜测是否属于热点。

保留 `model.ap` 状态检查。配置写入继续校验当前 `X-Setup-Session`。不能通过移除 `on_ap()`、仅检查 `Host` 或信任转发请求头来解除 403。

归一化本地地址只修复结构误读，不代表已经证明真实入站接口隔离。真机还需验证 STA 通道，包括人为路由到 AP 地址的情况；如可跨接口访问，应进一步使用可验证的入站接口信息或接口限定方案。

### 4.2 拒绝原因与诊断

将单一拒绝结果细分为可定位的原因，例如：

- 配网会话未开启。
- AP 接口地址读取失败。
- 套接字本地地址读取失败。
- 地址族不支持或结构长度不足。
- 本地地址与 AP 地址不匹配。

保留 HTTP 403。网页提示使用简体中文，并给出重新连接当前屏幕所示热点的操作入口。会话过期与通道不匹配应有不同的原因码。

诊断只记录拒绝原因、地址族、地址长度，以及必要的本地接口地址。实际构建结果需记录 `CONFIG_LWIP_IPV6` 的值。不得记录 Wi-Fi 密码、配网会话令牌、设备令牌或私有正文。

### 4.3 变更范围

主要修改点预计位于 `firmware/device/main/network.cpp` 的地址判断和错误分支，以及相关主机回归测试。保持现有配网 API 路径、网络配置格式和 NVS 数据兼容。本轮不通过关闭整个项目的 IPv6 功能来规避错误。

## 5. P1：入口和失败反馈

### 5.1 按路径分发请求

当前 ESP-IDF 按 URL 路径匹配处理函数，而业务函数使用完整 `req->uri` 比较。带查询参数的首页或状态请求会落入扫描分支。[S1][S6]

实施时提取路径部分，再按“方法 + 路径”明确分发。查询参数不得改变接口身份。

| 请求 | 目标行为 |
|---|---|
| `GET /`、`GET /?source=setup` | 返回同一配网页 HTML |
| `GET /api/status` 及带查询参数的同路径 | 返回状态、会话及已保存网络名称 |
| `GET /api/scan` | 执行扫描并返回网络列表 |
| 未知 `/api/*` 路径 | 返回 404，不执行扫描、不跳转门户 |
| 路径存在但方法错误 | 返回 405 |

为路径解析设置明确的长度边界。请求头和查询参数不能替代真实通道及配网会话检查。

### 5.2 热点启动与操作接收

逐项检查热点模式切换、配置和启动的返回结果。启动结果明确之前，不将状态无条件置为“已开启”。失败时恢复可解释的状态，屏幕和 USB 返回准确结果；地址从 AP 接口实际状态读取。

操作入队应返回成功或失败。队列满、已有连接操作正在执行时，网页不得收到虚假的 `accepted=true`。重复提交应被限制或明确拒绝。

### 5.3 网页连接状态

保留现有 `status` 字段的兼容性；如需机器可读状态，追加字段，不直接改变已有字段类型。

网页提交后禁用重复提交，并在当前配网会话内获取连接结果，区分正在连接、认证失败、DHCP 超时、配置保存失败和成功。失败后恢复输入，允许修改密码重试。

只有关联、DHCP 和配置保存都成功，才关闭热点并报告完成。热点断开或状态请求失败本身不等于配网成功。成功关闭热点前，尽可能让网页取得明确结果，最终结果同时保留在设备屏幕。

状态轮询应有次数或时间上限。后台轮询不刷新“用户无操作”的五分钟计时，避免打开一个网页就永久保持热点；真实提交和手动操作才更新活动时间。

先按响应类型解析错误正文，再检查状态码，避免将服务端纯文本错误变成难以理解的 JSON 解析异常。Wi-Fi 连接结果与代理 HTTPS、飞书授权结果分别显示。

## 6. P2：手机配网门户兼容

选定 Android、iOS 和 macOS 的测试版本，处理其实际使用的探测路径，例如 `/generate_204`、`/hotspot-detect.html` 和 `/connecttest.txt`。仅在有效配网会话及允许的访问通道内，将这些 HTTP 请求引导至设备配网页。

如果要支持任意 HTTP 域名访问，另需实现只在热点会话内运行的 DNS 响应；仅注册探测路径不能保证自动弹窗。该能力应独立验证，不承诺所有系统版本都会自动打开。

重定向目标使用设备自身的受控地址，不使用外部 `Host` 或用户参数生成跳转目标。API 错误继续返回 API 错误，不统一重定向。不拦截 HTTPS，不要求用户绕过证书校验。根地址手动配网始终保留。

## 7. 验收与证据

### 7.1 主机回归

回归应调用实际地址判断函数或其真实调用路径。双栈用例使用真实套接字，或使用已核对 lwIP 布局和截断行为的替身。仅让替身直接返回“正确 IPv4 地址”无法覆盖本次缺陷。

| 编号 | 场景 | 通过条件 |
|---|---|---|
| H-01 | AP 会话开启，IPv4 本地地址等于 AP 地址 | 检查通过 |
| H-02 | 同一合法 IPv4 请求由双栈套接字接受 | 映射地址被正确识别，检查通过 |
| H-03 | AP 会话关闭或本地地址属于 STA | 检查拒绝，原因正确 |
| H-04 | 未知地址族、原生 IPv6、截断地址或接口读取失败 | 安全失败，无错误结构读取 |
| H-05 | 伪造 `Host` 或转发请求头，使用错误或过期会话 | 不能改变通道判断；写配置被拒绝 |
| H-06 | 根路径和状态路径分别添加查询参数 | 返回正确资源；未知 API 不进入扫描 |
| H-07 | 热点启动失败、队列满、连接中重复提交 | 不虚报启动成功或已接收 |
| H-08 | 认证失败、DHCP 失败、保存失败及后台状态轮询 | 错误可恢复；轮询不阻止会话超时关闭 |

H-01 至 H-05 属于 P0 验收；H-06 至 H-08 随 P1 交付。实施前应先证明 H-02 在原实现中失败，修复后再证明通过，并保留非热点访问仍被拒绝的结果。

### 7.2 真机验收

1. 记录基线与候选固件 SHA、ESP-IDF 版本、实际 IPv6 配置、手机系统及浏览器版本。
2. 通过设备菜单或实体双键进入配网，核对屏幕与实际热点名称、密码及地址。
3. 手机连接热点，手动打开 `http://192.168.4.1/`，确认 HTTP 200 和配网页；同时验证双栈配置下的地址判断。
4. 同时验证 STA 通道和跨接口路由场景，不以页面可以打开代替写配置的访问控制验证。
5. 扫描并连接一组真实 2.4 GHz WPA2 网络，核对 DHCP、配置保存和热点关闭。另用错误密码、网络不存在及 DHCP 失败验证重试与旧配置保留。
6. 对照 AC-32 验证隐藏 SSID、第六组网络的明确替换，以及 Wi-Fi 已连但代理不可达的独立反馈。
7. 对照 AC-01、AC-31 完成三次完全断电重启与 A→B→A 环境切换，核对网络、代理绑定、内容缓存和阅读位置。
8. 验证五分钟无操作关闭，包含“网页保持打开并轮询”的情况；再次进入配网后旧会话失效。
9. P2 实施后，记录选定系统的探测请求和门户表现，同时回归手动地址访问。

保留必要的 HTTP 状态、诊断原因、页面截图和数据保留检查结果。主机测试通过、固件构建通过、真机配网通过分别记录；未执行的用例保持“待验证”。

如果后续实施涉及主循环、显示或电源等待，应先遵循 [固件维护要求](../firmware/device/AGENTS.md) 和 [终端按键与刷新策略](device-refresh.md)，再运行对应回归。仅修改网络地址判断时，优先运行相关回归和固件构建，不因本文是文档变更而声称运行了固件测试。

## 8. 交付与回退

P0、P1、P2 分别保留提交和验证边界。每次交付记录变更文件、源码 SHA、测试结果和仍未覆盖的真机场景。

固件交付沿用现有分区和配置格式。烧录前备份并校验当前应用槽；正常升级只更新应用槽，保留网络、绑定和内容。回退到已备份应用可恢复原实现，但其双栈误判也会一并恢复，不能作为问题已修复的证据。

本方案不扩大到代理重构、远程 Wi-Fi 管理或 OTA 平台建设。本次文档创建不触发上述实施、构建或烧录步骤。
