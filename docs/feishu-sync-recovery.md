# 飞书同步失败与自动恢复

日期：2026-10-27。适用于代理端；终端固件仍为 0.2.8。

## 本次原因与处理结果

手动同步时有两篇文档保留 `UPSTREAM_TIMEOUT`、连续失败次数为 1。两篇均有完整旧快照，目录发现没有失败。直接复查飞书接口，两篇分别约 3.1 秒完成元数据、正文块、修订号复核，正文分别为 87 和 31 块，没有截断或权限错误。

原服务日志只记录启动信息，数据库只有通用超时错误，无法区分原先是连接失败、上游 5xx、单请求 15 秒超时，还是整篇 25 秒预算耗尽。因此不将某一项推测当作已证实的网络原因。已确认的恢复缺陷是：GET 未做瞬时重试；失败退避沿用正常更新间隔，首次就等待三小时；手动刷新把所有正文设为立即执行后，失败文档与正常文档按 ID 排队，不能优先恢复。此外，暂时超时的目录分页会被标记为结束，等下一轮扫描才恢复。

修复后已备份数据库并重启本机代理，通过控制台使用的手动刷新 API 重新同步。07:45:29 和 07:45:35，两篇均产生恢复日志，错误和失败次数清零；控制台 API 返回 454 篇目录、454 篇已有正文、失败 0，源错误为空。两篇正文预览均为 HTTP 200，快照 SHA-256 与引用一致。这里的 454 篇正文是已有缓存总数，本次全量刷新仍由后台逐篇继续，不代表这 454 篇已全部重新读取。

飞书应用配置和设备绑定保持一致，正常检查间隔仍为 10,800 秒。HTTPS 设备入口通过原 CA 验证，未鉴权请求返回 401。私有备份、逐请求诊断、测试结果及运行日志位于 `artifacts/feishu-sync-2026-10-27/`，不提交凭据或文档正文。

## 必须保留的恢复规则

| 场景 | 行为 |
|---|---|
| 健康目录与正文 | 每三小时检查；初次缺失正文及手动刷新立即排队 |
| GET 连接失败、超时或上游 5xx | 间隔一秒，在失败的同一分页重试一次；不重新开始整篇读取 |
| 仍然超时 | 独立退避 30、60、120、240、480、900 秒，此后保持最多 900 秒 |
| 修订号在读取期间变化 | 不提交混合版本，5 秒起退避，最长 60 秒 |
| HTTP 429 | 不立即重试整个源；等待至少服务端 `Retry-After`，源级调度另加少量随机延迟 |
| 飞书业务错误码 `99991400` | 按限流处理，至少等待 60 秒；不能误报为权限不足 |
| 权限、授权或永久性格式错误 | 保留旧内容，维持较慢的重试或提示修复授权；不高频循环 |
| 到期失败文档 | 优先于正常文档恢复；未来的退避期限仍必须遵守 |
| 暂时失败的目录分页 | 持久化游标、失败次数与下次时间；继续其他目录和正文，不删除旧文档。同一轮最多尝试六次，耗尽后保留部分失败状态，交给下一轮扫描，避免永久阻塞健康目录的后续检查 |
| 手动刷新 | 提前唤醒待重试正文及未完成目录；仍遵守遇到的新限流响应 |
| 成功恢复 | 原子提交快照并清空错误、失败次数，恢复三小时正常周期 |

只有幂等 GET 允许上述一次瞬时重试。OAuth 换票、刷新凭据、配置写入不纳入该循环；访问令牌失效仍沿用原有并发合并和一次刷新重放规则。具体限流码依据[飞书官方通用错误码](https://open.feishu.cn/document/server-docs/api-call-guide/generic-error-code)。

单请求仍限制为 15 秒，目录分页允许 35 秒，含多次请求的单篇正文允许 120 秒，飞书工作任务为 180 秒。外层预算必须容纳内层分页及重试，且始终有上限；RSS 的 60 秒工作预算保留。失败只影响对应内容或限流中的源，不删除旧快照；配置代次检查和修订号围栏必须保留。

目录队列增加 `due` / `failures` 字段，启动时幂等迁移，保留原游标。所有未完成分支的最早重试时间参与调度，等待期间不能每秒空转，也不能让一个失败分支阻塞其他分支。
